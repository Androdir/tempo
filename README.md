# Tempo — Local Productivity Tracker

A local-first desktop productivity tracker. It samples your **active window** every
10 seconds, classifies time by app and category, and shows a clean daily dashboard.

**Everything stays on your machine.** No cloud, no account, no telemetry.

- 🔒 **No keystrokes recorded** — idle is detected from the OS "time since last input" value only.
- 🔇 **No audio, no clipboard, no mouse coordinates.**
- 📦 **No network calls.** Data lives in a local SQLite file.

---

## Features

### Core tracking
- **10-second window sampling** — timestamp, app/process name, window title, duration, idle/active.
- **Privacy-preserving idle detection** — uses `GetLastInputInfo` (Windows), which reports only
  *how long* since the last input, never *what* the input was.
- **Browser tracking** — optional Chrome extension samples the active tab and page title.
- **Smart screen OCR** — optional local screenshot + OCR (Windows only, OFF by default).

### Dashboard & reporting
- **Today dashboard** — total tracked time, idle time, time per app, time per category, and a
  productive / neutral / distracting split.
- **Proof-of-Work Timeline** — the real flow of your day as continuous, merged activity blocks
  (start/end/duration, category, project, classifier), with highlights (longest focus, biggest
  leak, first work) and inline corrections — so you can tell genuine work from feeling busy.
- **Proof-of-Output detection** — a local folder watcher records actual outputs (video exports,
  code changes, documents, downloads), links them to the activity around them, and feeds your
  score, timeline and streaks. Metadata only — file contents are never read.
- **Daily Lock-In Plan** — a concrete plan for tomorrow (main mission, 2 secondaries, first block,
  distraction rule, focus-mode setup, a trap to avoid, a roast line) from the local LLM or a
  rule-based fallback; editable, and one click sends it to tomorrow's goals.
- **Streaks** — consistency on meaningful behaviours (posted video, studied, gym, main goal,
  60+ min focus block, no-major-distraction day…) with current/best runs and a 4-week heatmap.
- **Activity Log** — all desktop/web/screen samples with final classification, project match,
  confidence score, and ability to manually correct any entry.
- **Browser Activity** — per-website time breakdown; click a site to see recent pages with
  summaries, keywords, and captured excerpts (if enabled).
- **Daily Score** — a 0–100 score from configurable rules (time-based + goal/check-in based),
  with verdict, top wins, biggest leaks, and suggested fixes.
- **Daily AI Review** — generated by the local Ollama LLM (if enabled) or rule-based fallback:
  one-sentence verdict, 3 wins, 3 problems, goal for tomorrow, roast line. Cached per day.
- **Weekly Review** — 7-day roll-up: productive vs. distraction time, study time, videos posted,
  best & worst day, most common time leak, per-day score chart.

### Categorization & projects
- **Manual categories** — tag each app/site as `productive`, `study`, `business`, `neutral`,
  `distraction`, or `recovery`. Rules are saved locally and reused.
- **Hybrid classifier** — rule-based → LLM (if confidence < 0.75) → manual correction override.
  Classifier source shown with badge: 🏷️ rule, 🤖 LLM, ✏️ manual.
- **Projects & Goals** — define projects (name, category, keywords, related apps/domains),
  activity is matched by app/keyword signals and assigned a confidence score (0–100).
- **Daily Goals** — set daily missions with priority, optional duration, completion checkbox.
  Mark as recurring (↻) to repeat daily; **Copy yesterday** to bulk-add.
- **Quick check-ins** — one-tap buttons for untracked activities (video posted, gym, wrestling,
  studied, edited video, analysed content).

### Accountability (soft enforcement)
- **Distraction warnings** — when spending >X continuous minutes on a distracting app/site,
  get a desktop notification + in-app toast asking *"Still intentional?"*. Re-warns at multiples
  (40m, 60m…). Actions: *Snooze 30m* or *It's intentional* (mutes that app for 1h).
- **Focus Mode** — start a session with a goal, duration, allowed/blocked app & site lists.
  Live countdown ring; soft nudges if you open blocked targets. Session summary on end.
- **End-of-day popup** — at your chosen time, the daily AI review pops up automatically
  (fires once per day).
- **Weekly review page** — 7-day trends and top performers/leaks.

### Privacy & data management
- **Capture policy** — toggle page-text capture per-domain (off by default), with auto-blocklist
  for banking/payment/health/email. Content script reads only visible text, never form fields.
- **Smart tracking warning** — prominently warns before enabling screenshot OCR.
- **Data retention** — keep raw samples for N days (default 90; 0 = forever). Prune on startup
  or on demand. Goals, scores, reviews, rules always kept.
- **Local OCR** — Windows built-in engine, no network, screenshots never touch disk.

### Multi-device (optional Tempo Hub)
- **Tempo Hub** — an optional always-on server (e.g. a **Raspberry Pi 500**) that several devices
  push to and that serves one shared dashboard. Local-only mode is unchanged. Event-based sync with
  offline buffering, dedup, and per-device tokens.
- **Phone tracking (Android)** — a lightweight native app reads per-app foreground time and adds it
  to the hub; the same app shows the dashboard in a WebView. (Check-ins, goals and notes logged on
  the desktop also sync to the hub.)
- **Per-device breakdown** — the hub dashboard shows active time per device (desktop vs phone), idle
  excluded, so you can see exactly what each one contributed.
- **Cross-device focus** — a focus session's adherence is scored across every device (overlap-aware),
  so phone scrolling counts against a desktop lock-in.
- **Media-aware idle** — a video or lecture playing keeps time active even with no keyboard/mouse
  input (toggle-able).

## Running the app

### 1. Install & start the desktop app

```bash
npm install          # install frontend deps
npm run app          # = tauri dev: launches the desktop app
```

**First run** compiles Rust (2–3 minutes). Subsequent runs are fast.

The tracker starts immediately — leave it running, use your computer normally, and watch the
dashboard refresh live.

On an empty day, click **"Load sample data"** on the Dashboard to preview the UI.

### 2. (Optional) Set up browser tracking with the Chrome extension

The Chrome extension tracks your active browser tab (while Chrome is the focused desktop window)
and sends samples to the app's local server over `http://127.0.0.1:48710`.

**Setup steps:**

1. **Get the endpoint + token** from the app:
   - Open the app (from step 1 above).
   - Go to **Privacy & Settings**.
   - Under **Browser extension**, copy the **Endpoint** (e.g., `http://127.0.0.1:48710`) and **Token**.

2. **Load the extension into Chrome:**
   - Open `chrome://extensions` in Chrome.
   - Enable **Developer mode** (toggle, top-right).
   - Click **Load unpacked**.
   - Navigate to the `extension/` folder in this repo and select it.
   - The extension will appear in your extensions list.

3. **Configure the extension:**
   - Click the extension icon → **Options** (or right-click → Manage extension → Extension options).
   - Paste the **Endpoint** and **Token** from step 1.
   - (Optional) Enable **Capture page content** to store text summaries + keywords; keep OFF for
     pure domain/URL tracking.
   - Click **Test connection** — it should say "Connected ✓".

4. **Start tracking:**
   - The extension is now tracking. Visit websites normally; samples arrive every ~10 seconds
     while Chrome is focused.
   - View them on **Browser Activity** page in the app.

For full extension details, see [`extension/README.md`](extension/README.md).

### 3. (Optional) Enable local LLM classification with Ollama

Refines the app's classification (rule-based → LLM for ambiguous cases) using a locally-running
Ollama server. Completely optional; the app works fine with rule-based only.

**Setup steps:**

1. **Install & run Ollama:**
   ```bash
   # Download from https://ollama.com
   ollama serve                 # starts the server on http://localhost:11434
   ```
   (Ollama runs in the background; you can close the terminal after starting.)

2. **Pull a model** (in another terminal):
   ```bash
   ollama pull llama3.1:8b      # ~4.7 GB; or qwen2.5:7b (~5 GB)
   ```

3. **Configure the app:**
   - Open the app's **Privacy & Settings**.
   - Under **Local AI classification (Ollama)**, you'll see:
     - **URL** (defaults to `http://localhost:11434`)
     - **Model** (type the model name, e.g., `llama3.1:8b`)
   - Click **Test connection** — it should verify the model is available.
   - Once connected, the LLM background worker starts; new/ambiguous samples get refined
     classifications (shown with 🤖 badge in the Activity Log).

### 4. (Optional) Enable smart screen OCR (Windows only)

Periodically captures and OCRs the active window for better context (off by default).

**Setup:**
- Open **Privacy & Settings**.
- Under **Personal Smart Tracking Mode**, toggle ON.
- Set the interval (default 60s, range 10–3600s).
- The app warns about privacy implications; read them carefully.

**Data handled:** Only timestamp, app, title, OCR summary (≤300 chars), keywords, and category
are stored — never the screenshot. Sensitive data (card numbers, SSNs, passwords) are detected
and the entire sample is discarded. Captures are skipped while idle.

## How it works

### Sampling loop (`tracker.rs`)
Every 10 seconds a background thread:
1. reads idle time (GetLastInputInfo) and decides `is_idle`.
2. reads the foreground window's app name + title.
3. inserts one row into `activity_log`.
4. emits a `tracking-updated` event so the dashboard refreshes.

### Browser extension (`extension/`, `server.rs`, `ingest.rs`)
If the Chrome extension is loaded and configured:
- Every ~10 seconds it sends the active tab's domain, URL, title, and optional page content to
  `POST /ingest` on the app's loopback server.
- The app validates the request token, parses the payload, and stores it in `browser_activity`.
- Page content is optional (capture policy); by default only domain/URL/title are tracked.

### Hybrid classification (`rules.rs`, `llm.rs`, `commands.rs`)
When you view an activity sample (Activity Log, Activity Details, dashboard), the app classifies
it using a three-tier system:

1. **Rule-based** (`classify.rs`): app/domain rules, title keywords, project matching.
   Returns a category + confidence (0–1).
   - Confidence ≥ 0.8 → use this, skip LLM.
   - Confidence < 0.75 or ambiguous (e.g., OCR conflict) → continue to tier 2.

2. **LLM** (if enabled, `llm.rs`): a background worker classifies blocks with context
   (neighbors, projects as goals) and caches the verdict in `llm_classification`.
   - On cache hit → use cached LLM result (shown with 🤖 badge).
   - On cache miss or Ollama down → fall back to rule-based, no crash.

3. **Manual correction**: In the Activity Details drawer, you can click the classifier badge
   (🏷️ / 🤖 / ✏️) to manually override any category. Stored in `manual_corrections` table.
   - Next read uses the manual category (shown with ✏️ badge).

### Aggregation & scoring
- `collect_blocks_for_day()` groups today's active samples by app/domain.
- `compute_stats_for_day()` applies the hybrid classifier to each block, counts minutes per
  *final* category (after manual override), and rolls into buckets.
- `get_daily_score()` runs configurable rules on the stats (time-based + goal/check-in based)
  and returns a 0–100 score + verdict + breakdown.
- `get_daily_review()` feeds the score, stats, goals, notes into the Ollama LLM (or rule-based
  fallback) and returns a structured review.

### Accountability watcher (`accountability.rs`)
A background thread ticks every 10 seconds and checks:
1. **Distraction warnings** — if current foreground is categorized as "distraction" and
   you've been on it continuously for >X minutes, emit a `distraction-warning` event
   (unless currently snoozed or muted for that app).
2. **Focus mode violations** — if a focus session is active and you drift onto a blocked app
   or (with allowlist) off-focus sites, emit a `focus-violation` event (throttled).
3. **End-of-day popup** — if your configured EOD time has passed and the popup hasn't fired
   today, emit a `daily-review-due` event.

All events are received by the frontend's `AccountabilityLayer`, which shows toasts and modals.
Snooze/mute state is persisted in `app_settings`, checked by the watcher on each tick.

### Proof-of-Work Timeline (`get_timeline_for_day`)
Where the Activity Log aggregates the day by app, the Timeline shows its **flow**: raw samples
(desktop + browser + screen-OCR) classified with the same hybrid system, then merged into
**continuous blocks**. A new block starts on a change of app/domain, category, project, or idle
status, or when the gap between samples exceeds the configurable threshold (default **2 min**).
Each lane is merged independently and a desktop "Chrome" run is dropped when the browser lane
already covers that time (so you see the tab, not the shell). The backend flags the day's
highlights — **longest productive block, biggest distraction, first productive block,
goal-related** (project matches a goal) and **output-linked** (content-business work) — and the
page lets you filter (category / source / project / app) and **correct any block inline** (the
correction reuses the same `manual_corrections` + rule system as the Activity Log). Self-reported
outputs (videos posted, etc.) have no timestamps, so they're shown as a summary strip rather than
positioned blocks. Unit tests cover run-merging, category splits, and the browser/desktop dedupe.

### Proof-of-output detection (`output.rs`)
A polling folder watcher (chosen over an OS file-watch dependency for robustness and testability)
scans your **explicitly added** watched folders every ~20s and records new/changed files as
`output_events` — **metadata only**, file contents are never read. Each folder has a label,
project, output type, on/off switch, extension filter, minimum size, and a *settle* (debounce)
time so half-finished exports aren't counted. Detection is idempotent on `(file_path, modified_at)`
and only fires for files modified *after* the folder was added, so existing history isn't imported.
Each event is then **linked** to the app/domain active within ±10 min (`link_outputs_for_day`), so
a `.mp4` export ties to your Premiere block. Outputs feed the **Daily Score** (a real export is
stronger proof than time spent), show as **Timeline markers**, and satisfy **streaks**. Disabling a
folder (or the master toggle) stops detection. Unit tests cover extension classification, the
min-size/debounce/disabled rules, history-skipping, and activity linking.

### Streaks (`streaks.rs`)
Twelve seeded streaks track consistency on what matters (posted video, studied, gym, wrestling,
completed main goal, 60+ min coding/study, 90+ min business, a 60+ min focus block, a
no-major-distraction day…). For each of the last 28 days a `DayMetrics` is built from check-ins +
category minutes + block maxima + output counts, and each streak's condition is evaluated. The
**current run** counts consecutive met days ending today (or yesterday, if today's still in
progress); **best** is the longest run, persisted so it survives the window. Streaks are
enable/disable-able and their thresholds editable. Pure run-maths and condition evaluation are
unit-tested; integration tests check consecutive/broken runs and the disabled filter.

### Daily Lock-In Plan (`lockin.rs`)
A concrete plan for **tomorrow**, generated from today: score, completed/missed goals, biggest
distraction, detected outputs, recurring goals and your notes. With Ollama enabled it asks the
local LLM for strict JSON (`main_mission`, two `secondary_missions`, `first_block`,
`distraction_rule`, `focus_mode_suggestion`, `avoid_trap`, `roast_line`); otherwise it uses
rule-based templates that read the same inputs. Plans are cached per day, fully editable (which
marks them `manual`), and one click copies the missions into the next day's goals. The Dashboard
surfaces yesterday's plan as "today's plan"; the Daily Goals page has a "Use suggested plan"
button. Unit tests cover the rule fallback, JSON parsing, per-day caching, edit persistence and the
goal copy.

## Database schema

Stored in a local SQLite file (see **Data location** below).

```sql
-- Active window samples (desktop)
CREATE TABLE activity_log (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp        TEXT    NOT NULL,           -- RFC3339 UTC instant
    day              TEXT    NOT NULL,           -- local YYYY-MM-DD
    app_name         TEXT    NOT NULL,
    window_title     TEXT    NOT NULL,
    duration_seconds INTEGER NOT NULL,           -- ~10 per sample
    is_idle          INTEGER NOT NULL DEFAULT 0  -- 0 = active, 1 = idle
);

-- Browser samples (from extension)
CREATE TABLE browser_activity (
    id                       INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp                TEXT NOT NULL,
    day                      TEXT NOT NULL,
    domain                   TEXT NOT NULL,
    url                      TEXT NOT NULL,
    page_title               TEXT NOT NULL,
    duration_seconds         INTEGER NOT NULL,
    content_type             TEXT,
    content_capture_enabled  INTEGER NOT NULL,
    content_summary          TEXT,
    detected_keywords        TEXT,
    raw_text_excerpt         TEXT,
    is_idle                  INTEGER NOT NULL DEFAULT 0
);

-- Screen OCR samples (if smart tracking enabled)
CREATE TABLE smart_activity (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp        TEXT NOT NULL,
    day              TEXT NOT NULL,
    app_name         TEXT NOT NULL,
    window_title     TEXT NOT NULL,
    ocr_summary      TEXT NOT NULL,
    detected_keywords TEXT,
    is_idle          INTEGER NOT NULL DEFAULT 0
);

-- User-defined category rules
CREATE TABLE category_rules (
    app_name   TEXT PRIMARY KEY,
    category   TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE domain_rules (
    domain        TEXT PRIMARY KEY,
    category      TEXT NOT NULL,
    capture_mode  TEXT NOT NULL,
    ai_review     INTEGER NOT NULL DEFAULT 0,
    updated_at    TEXT NOT NULL
);

-- LLM classification cache
CREATE TABLE llm_classification (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    day           TEXT NOT NULL,
    key           TEXT NOT NULL,
    is_web        INTEGER NOT NULL,
    category      TEXT NOT NULL,
    confidence    REAL NOT NULL,
    project       TEXT,
    reason        TEXT,
    created_at    TEXT NOT NULL
);

-- Manual category overrides
CREATE TABLE manual_corrections (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    day        TEXT NOT NULL,
    key        TEXT NOT NULL,
    is_web     INTEGER NOT NULL,
    category   TEXT NOT NULL,
    corrected_at TEXT NOT NULL
);

-- Daily goals
CREATE TABLE goals (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    day        TEXT NOT NULL,
    title      TEXT NOT NULL,
    project    TEXT,
    target_minutes INTEGER,
    priority   TEXT NOT NULL,
    completed  INTEGER NOT NULL,
    recurring  INTEGER NOT NULL DEFAULT 0,
    sort_order INTEGER NOT NULL,
    created_at TEXT NOT NULL
);

-- Daily check-ins (things tracker can't see)
CREATE TABLE daily_checkin (
    day                 TEXT PRIMARY KEY,
    main_goal_completed INTEGER NOT NULL DEFAULT 0,
    videos_posted       INTEGER NOT NULL DEFAULT 0,
    gym_logged          INTEGER NOT NULL DEFAULT 0,
    wrestled            INTEGER NOT NULL DEFAULT 0,
    studied             INTEGER NOT NULL DEFAULT 0,
    edited_video        INTEGER NOT NULL DEFAULT 0,
    analysed_content    INTEGER NOT NULL DEFAULT 0,
    notes               TEXT
);

-- Focus mode sessions
CREATE TABLE focus_sessions (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    goal             TEXT,
    started_at       TEXT NOT NULL,
    duration_minutes INTEGER NOT NULL,
    ends_at          TEXT NOT NULL,
    allowed          TEXT,                       -- JSON array
    blocked          TEXT,                       -- JSON array
    status           TEXT NOT NULL,              -- active|completed|ended
    ended_at         TEXT
);

-- Key/value settings (privacy toggles, tokens, snooze/mute state, etc.)
CREATE TABLE app_settings (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

-- LLM error log
CREATE TABLE llm_errors (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TEXT NOT NULL,
    context   TEXT,
    message   TEXT NOT NULL
);
```

### Categories → buckets

| Category      | Bucket       |
| ------------- | ------------ |
| productive    | Productive   |
| study         | Productive   |
| business      | Productive   |
| neutral       | Neutral      |
| recovery      | Neutral      |
| distraction   | Distracting  |
| *(untagged)*  | Neutral      |

This mapping lives in **one place per side**: `bucket_for()` in `models.rs` and
`CATEGORY_META` in `categories.ts` — keep them in sync.

## Data location

The SQLite database is created at the OS app-data directory:

- **Windows:** `%APPDATA%\com.local.productivitytracker\productivity.db`
- **macOS:** `~/Library/Application Support/com.local.productivitytracker/productivity.db`
- **Linux:** `~/.local/share/com.local.productivitytracker/productivity.db`

Delete that file to wipe all history. Nothing is stored anywhere else.

## Troubleshooting

### App won't start
- Check you have Rust stable: `rustc --version`.
- On Windows, install MSVC Build Tools ("Desktop development with C++").
- Delete `src-tauri/target/` and try `npm run app` again (full rebuild).

### Extension not connecting
- Verify the **Token** is pasted correctly (copy from Privacy & Settings in the app).
- Check the **Endpoint** matches (default `http://127.0.0.1:48710`).
- Make sure the app is running (the server must be listening).
- Click **Test connection** in the extension options.

### LLM classification not working
- Ensure Ollama is running: `ollama serve` in a terminal.
- Check the URL in **Privacy & Settings** is correct (`http://localhost:11434`).
- Verify the model exists: `ollama list` in a terminal.
- Click **Test connection** in the app's LLM settings.

### Smart OCR slow or not working (Windows only)
- Smart tracking is OFF by default. Enable it in **Privacy & Settings** if you want it.
- On slower machines, increase the interval (60s default).
- The first capture may take a few seconds to initialize Windows.Media.Ocr.

## Tempo Hub — optional central server (Raspberry Pi)

By default Tempo is **100% local** — nothing changes. Optionally, you can run a **Tempo Hub**
on a Raspberry Pi (or any always-on box) so several devices push activity into **one shared
database** and view **one shared dashboard**. Local-only mode keeps working unchanged.

### Set everything up (desktop · Raspberry Pi 500 · phone)

Pick your level — each builds on the last:

- **Just the desktop?** Install the desktop app ([Running the app](#running-the-app)) and you're
  done; everything is local. The steps below add the optional hub + phone.

**A — The hub on a Raspberry Pi 500.** (A Pi 500 is a Pi 5 inside → arm64, so Docker just works.
Any always-on Linux box works too.)

1. Install Docker on Raspberry Pi OS (64-bit): `curl -fsSL https://get.docker.com | sh`, then
   `sudo apt install -y docker-compose-plugin`.
2. Clone and start it:
   ```bash
   git clone <this repo> && cd ai_usage_tracker_app
   echo "TEMPO_PAIRING_SECRET=$(openssl rand -hex 24)" > .env   # a strong random secret
   docker compose up -d --build      # builds the dashboard + hub for arm64, serves on :7700
   cat .env                          # copy the pairing secret — you'll enter it on each device
   ```
3. **Reach it privately.** Install [Tailscale](https://tailscale.com) on the Pi *and* each device
   (`curl -fsSL https://tailscale.com/install.sh | sh`). Your hub URL is then
   `http://<pi-tailscale-name>:7700`. (On a trusted home LAN you can use the Pi's LAN IP instead —
   but never port-forward to the internet.)
4. Open `http://<hub>:7700` in a browser and enter the pairing secret once.

**B — Point the desktop at the hub.**

1. Install + run the desktop app ([Running the app](#running-the-app)).
2. **Privacy & Settings → Sync**: set Mode to *Connect to Tempo Hub*, enter the hub URL + pairing
   secret, **Pair**, then **Import history** to backfill. It keeps tracking locally and uploads in
   the background, buffering through any hub downtime.

**C — Track your phone (Android).**

1. Open the [`android/`](android/) project in **Android Studio** and **Run ▶** on your phone
   (builds as-is with the Android SDK — see [`android/README.md`](android/README.md)).
2. In the app: **Grant usage access**, enter the same hub URL + pairing secret, **Pair & start
   tracking**. Phone app-usage now flows to the hub, and the app shows the shared dashboard.

The desktop app keeps its own local dashboard; the **hub dashboard** (browser or phone) shows
everything combined — per-device breakdown, cross-device focus, and check-ins/goals/notes from any
device. (iOS can view the dashboard in Safari but can't track — Apple exposes no per-app usage API.)

### Architecture

```
 Desktop (Tauri tracker)  ──events──►              ┌──────────────────────┐
 Browser extension ──► desktop ──forwards──►       │   Tempo Hub (Pi)     │
 Phone browser  ──────────────────────────────────►│  REST API + dashboard│
                                                    │  shared SQLite DB    │
                                                    └──────────────────────┘
```

- The repo is a **Cargo workspace**: `crates/tempo-core` (GUI-free shared logic — DB, models,
  scoring, streaks, lock-in, aggregation, the sync-event model), `crates/tempo-hub` (the headless
  server), and `src-tauri` (the desktop app, which now depends on `tempo-core`).
- **Only event records sync — never raw SQLite files.** Each event is unique by
  `(device_id, event_id)`, so re-uploads are **never double-counted**. On the hub, events are
  projected into the same tables the desktop uses, so all existing aggregation just works and
  multi-device data simply sums.
- Clients **buffer offline**: if the hub is unreachable, events sit in a local `sync_queue` and
  upload on the next tick. Sync status (connected / offline / last sync / queued) is exposed to the UI.

### Security (read this)

- The hub **binds to `127.0.0.1` by default**; it prints a loud warning if you set
  `TEMPO_BIND=0.0.0.0`. In Docker it binds `0.0.0.0` *inside the container* — the host port mapping
  + your firewall control real exposure. **Never expose it to the internet.**
- For remote access, use **[Tailscale](https://tailscale.com)** (or a VPN) and reach the hub on its
  private IP. Don't port-forward.
- Auth: a **pairing secret** (admin) exchanges for a **per-device token**; only the token's
  **SHA-256 hash** is stored. Devices can be **revoked**; unknown/revoked tokens are rejected. The
  device sync token is **separate** from the browser-extension loopback token. CORS is restricted and
  the pairing endpoint is rate-limited.

### Run Tempo Hub on Raspberry Pi

On the Pi (Docker + compose installed):

```bash
git clone <this repo> && cd ai_usage_tracker_app
echo "TEMPO_PAIRING_SECRET=$(openssl rand -hex 24)" > .env   # a strong random secret
docker compose up -d --build                                  # builds web + hub, starts on :7700
docker compose logs -f tempo-hub                              # note the secret you set in .env
```

The DB persists on the `tempo-data` volume. Open the dashboard at `http://<pi-ip>:7700` (or your
Tailscale IP) and enter the pairing secret once.

Run without Docker (any Linux/arm64):

```bash
npm run build                                  # build the dashboard → dist/
cargo build --release -p tempo-hub             # build only the hub (no Tauri deps)
TEMPO_PAIRING_SECRET=... TEMPO_BIND=0.0.0.0 TEMPO_STATIC_DIR=dist \
  ./target/release/tempo-hub
```

**Env vars:** `TEMPO_PAIRING_SECRET` (required) · `TEMPO_PORT` (7700) · `TEMPO_BIND` (127.0.0.1) ·
`TEMPO_DB` (path) · `TEMPO_STATIC_DIR` (dashboard dir) · `TEMPO_ALLOWED_ORIGINS` (CORS allowlist).

### Connect the desktop

In the desktop app's **Sync** settings: switch **Mode** to *Connect to Tempo Hub*, enter the hub
URL + pairing secret, and **Pair**. The desktop keeps tracking locally and uploads event batches in
the background; **Import history** re-sends existing local history once. The browser extension is
unchanged — it forwards to the desktop, which forwards to the hub.

### API (LAN/VPN only)

`GET /api/health` · `POST /api/pair` (secret → device token) · `POST /api/events` (Bearer device
token; dedup) · `POST /api/invoke` (dashboard transport) · `GET /api/devices` + `POST
/api/devices/revoke` (admin).

### Phone companion vs. phone tracking

The hub-served **website** works on any phone browser for the *companion* role: viewing the
dashboard/review, and editing check-ins / goals / notes. But a browser is sandboxed — it **cannot
see which apps you use on the phone**. To capture "I watched YouTube on my phone for 30 min" there
is a **native Android app** in [`android/`](android/): a lightweight Kotlin app that reads per-app
foreground time via `UsageStatsManager` (you grant it "Usage Access" once) and POSTs the same
`app_sample` event format to `/api/events`, then shows the hub dashboard in a WebView. Phone usage
flows through the existing ingest → `activity_log` → aggregation (including the cross-device focus
summary) with no hub changes. See [`android/README.md`](android/README.md) to build it in Android
Studio. (iOS exposes no equivalent per-app usage API, so iOS stays companion-only.)

### Hub endpoint coverage

The hub's `/api/invoke` now serves the **full read dashboard** from the same `tempo-core`
aggregation the desktop uses: **Today summary, Timeline, Daily Score, Streaks, Weekly Review,
Output Events, Daily Review, Lock-In Plan, and the Focus summary**, plus the goals / check-ins /
notes and the lock-in-plan writes (generate / save / copy-to-goals).

**Cross-device focus.** A focus session is started on the desktop (the phone has no tracker),
and once it ends it syncs to the hub as a single `focus` event. The hub then recomputes its
adherence over **every device's** activity in the session window — so if you lock in on your
desktop and then doomscroll Instagram on your phone, that time counts against the block. The
summary is **overlap-aware**: time where two devices (or the app + browser streams of one
device) were both active in the same wall-clock second is counted once, and the most-accountable
class wins (distraction > focus > other), so adherence never exceeds real elapsed time. Starting
a session is still desktop-only; live mirroring of an *in-progress* session to other devices is
future work.

A note on the AI features: the hub generates the Lock-In Plan and Daily Review through the
*same* code path as the desktop, so if no Ollama endpoint is reachable from the Pi it simply
returns the deterministic data-driven fallback (verdict, wins, problems, missions) rather than
an LLM-written one — no error, no blank page. The Pi doesn't run a model; to make these
LLM-written on the phone/web dashboard, point the hub at an Ollama you run elsewhere (your
desktop) with `TEMPO_LLM_ENABLED` / `TEMPO_OLLAMA_URL` / `TEMPO_OLLAMA_MODEL` (see
[Configuration reference](#configuration-reference)).

Native Android tracking now ships in [`android/`](android/). A PostgreSQL backend remains future
work, behind the seam already in place. (For a single-user personal hub, SQLite is the right fit — one file on the Docker
volume, the entire existing schema and aggregation reused, and it cross-compiles trivially for
ARM. Postgres would add a second container and a connection pool for concurrency this workload
doesn't have; the storage layer is seamed so it could be swapped later if that ever changed.)

## Configuration reference

### Hub — environment variables

| Variable | Default | What it does |
| --- | --- | --- |
| `TEMPO_PAIRING_SECRET` | *(required)* | Admin secret devices exchange for a token; also the dashboard password. Use a long random value (`openssl rand -hex 24`). |
| `TEMPO_PORT` | `7700` | Port the hub listens on. |
| `TEMPO_BIND` | `127.0.0.1` | Bind address. `0.0.0.0` exposes it to the network (prints a warning) — only behind Tailscale/a firewall. |
| `TEMPO_DB` | `/data/tempo.db` | SQLite database path (a Docker volume by default). |
| `TEMPO_STATIC_DIR` | `./web` | Folder of the built dashboard the hub serves. |
| `TEMPO_ALLOWED_ORIGINS` | same-origin | CORS allowlist for the dashboard. |
| `TEMPO_LLM_ENABLED` | off | Set `1` to let hub-served Daily Review / Lock-In Plan use an LLM (else deterministic fallback). |
| `TEMPO_OLLAMA_URL` | `localhost:11434` | Ollama endpoint the hub calls — point at a box that actually runs Ollama (e.g. your desktop). Loopback / LAN / Tailscale only. |
| `TEMPO_OLLAMA_MODEL` | `llama3.1:8b` | Model name the hub requests. |

> **LLM on the hub is optional and off by default — the Pi does not run a model.** To get
> LLM-written reviews on the phone/web dashboard, set the three vars above to point at an Ollama
> you run elsewhere (your desktop). Only **private** addresses are accepted — LAN or **Tailscale**
> (`100.64.0.0/10` + `*.ts.net`); public/cloud is refused. Run the desktop's Ollama with
> `OLLAMA_HOST=0.0.0.0`, keep the PC awake, and use its LAN or Tailscale IP. Block *classification*
> stays desktop-only regardless; without this, the hub's reviews/plans are the deterministic
> fallback (no error).

### Desktop — in-app settings (Privacy & Settings)

| Setting | Default | What it does |
| --- | --- | --- |
| Idle threshold | `60s` | Seconds of no input before a sample is marked idle (and excluded). Range 20–1800. |
| Count media as active | `on` | Keep time active when a video/music/lecture is playing, even with no input (Windows). |
| Data retention | `90 days` | How long raw samples are kept (`0` = forever). Goals/scores/reviews/rules always kept. |
| Capture page content | `off` | Let the extension read visible page text on allowed domains. |
| Store raw text | `off` | Keep the raw extracted text (vs. summary + keywords only). |
| Smart tracking (OCR) | `off` | Periodic local screenshot + OCR (Windows only). |
| Smart interval | `60s` | Seconds between OCR captures when enabled. |
| Local LLM (Ollama) | `off` | Use Ollama for classification + AI review/plan; set the URL (`localhost:11434`) + model (`llama3.1:8b`). |
| Distraction warning | `on`, `20m` | Warn after X continuous minutes on a distracting target. |
| End-of-day popup | `21:00` | When the daily review auto-pops (once per day). |
| Auto lock-in plan | `on` | Auto-generate tomorrow's plan at end of day. |
| **Sync** mode | `Local-only` | Switch to *Connect to Hub*, set the hub URL + pair; **Import history** re-sends everything (incl. today's check-ins/goals/notes). |

Configured on their own pages: **Daily Score** rule weights & thresholds, **Streaks** definitions
(enable + threshold), **Categories**/**Projects** classification rules.

### Phone (Android)

Hub URL + pairing secret are entered once in the app (stored encrypted). Tracking runs every ~15 min
via WorkManager; the browser-facing dashboard is the hub's web app.
